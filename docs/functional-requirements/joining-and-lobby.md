# Joining and Lobby

## Overview

Players reserve a place in a game's lobby with a PIN and a unique handle, while the
host receives authoritative presence updates and can remove players.

## User Stories

### US-010: Join a live game

**As a**
player

**I want**
to join a lobby using a PIN and handle name

**So that**
I can participate in the host's game.

### US-011: Manage the lobby

**As a**
host

**I want**
to see current player presence and remove inappropriate players

**So that**
I can prepare a suitable group before starting.

## Acceptance Criteria

- Given a valid PIN for a game in `LOBBY` with fewer than 500 non-removed players, when a player supplies a valid unique handle, then a seat and secure player session token are created in that game.
- Given a reserved player, when the player attaches through the realtime hub by `JoinGame` or `Reconnect`, then the host receives `ParticipantPresenceChanged`.
- Given a REST-only join, when no hub attachment has occurred, then no presence event is broadcast and the host can recover current presence through `GET /api/games/{id}`.
- Given a player in the lobby, when the host removes that player, then the player cannot rejoin the same game with the same handle.
- Given a connected player, when its current connection disconnects, then the connection is cleared, the absolute connected-player count and presence version are updated, and a disconnected presence event is broadcast.
- Given an owned game, when the host removes a player, then that player is marked removed, evicted from the player group, notified directly when connected, and represented in a versioned removal presence event.

## Business Rules

### FR-5: Joining a game

- Players join with a game PIN, embedded in a shared link or entered on the join page, and a handle name.
- PINs are short, generated by the server, and unique among unfinished games.
- Handle names are unique within a game without regard to case and must pass validation and sanitization.
- A game accepts at most 500 non-removed players.
- A valid PIN contains 4–8 digits.
- A nickname contains 2–30 characters and may contain Unicode letters, digits, spaces, underscores, periods, and hyphens.
- A REST join reserves a seat; successful hub attachment establishes presence.

### FR-5.1: Participant presence and removal

- Realtime presence is based on non-removed participants with an attached connection, not all reserved seats.
- Every effective attach, detach, or removal increments the game's monotonic presence version and publishes the resulting absolute connected-player count.
- Attaching a new connection replaces the participant's previous connection ID and updates `LastSeenAt`.
- A stale disconnect for a superseded connection is ignored and does not clear the current connection or emit another presence change.
- Only the owning host can remove a participant.
- Removing a player records the removal time, clears the connection, and prevents session-token reconnection.
- Repeating removal of an already removed player succeeds without another mutation or notification.

## Edge Cases

- A join is rejected for an invalid PIN, a game outside `LOBBY`, a duplicate case-insensitive handle, or a game that already has 500 non-removed players.
- After a game starts, new joins are rejected.
- Disconnecting or removing a player after the game starts does not create a joinable seat.
- A player removed by the host cannot reclaim the same handle in that game.
- Attaching a missing or removed participant is rejected with `Game.ParticipantRemoved`.
- Removing an unknown participant is rejected with `Game.ParticipantNotFound`.
