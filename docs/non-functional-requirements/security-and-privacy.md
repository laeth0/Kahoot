# Security and Privacy

## Purpose

Protect host credentials, player sessions, uploaded media, operational secrets,
and privileged game operations.

## NFR-4: Security

### NFR-4.1: Host Authentication

- Passwords must use a purpose-built password hash. BCrypt must use a work factor
  of at least 12; Argon2id is an acceptable alternative. Passwords must never be
  stored in plaintext or with a fast general-purpose hash.
- Access tokens must be short-lived JWTs signed with a strong secret supplied by
  configuration.
- Refresh tokens must be opaque, long-lived, stored only as hashes, single-use,
  and rotated. Reuse of a rotated token must revoke its token family.
- Login and refresh endpoints must be rate-limited and return generic failures
  that do not disclose whether an account exists.
- Passwords, password hashes, tokens, and secrets must never be logged.

### NFR-4.2: Authorization

- Every host operation requires authentication and authorization for the owned
  quiz or game.
- Players must not call host operations, submit for another participant, submit
  for another game, or answer a future or closed question.
- Player operations that mutate game state must validate the issued participant
  session token at the server boundary.

### NFR-4.3: Input and Transport

- All externally supplied PINs, display names, quiz content, question content,
  identifiers, and media must be validated at the server.
- Requests and payloads must have explicit size limits, and repeated answer
  attempts must be constrained.
- CORS must allow only configured frontend origins.
- Public production traffic must use HTTPS, and the application must interpret
  forwarded headers only through its trusted proxy configuration.
- Secrets must come from environment variables or approved configuration
  providers and must not appear in source control, frontend bundles, logs,
  errors, URLs, or health responses.

### NFR-4.4: Rate Limiting

- Authentication, join, and general API traffic must have separate policies
  appropriate to their risk and burst patterns.
- Rate-limit partitions must use the real client address after trusted forwarded
  headers are applied.
- The current authentication policy permits 10 requests per 5-minute fixed
  window per client and normalized username.
- The current join policy uses a per-client token bucket with a 1,200-request
  burst, 600 tokens replenished every 10 seconds, and a queue of 200.
- The current global policy uses a per-client token bucket with a 2,000-request
  burst, 1,000 tokens replenished every 10 seconds, and a queue of 200.
- The SignalR answer operation must retain its per-connection guard of five
  submissions per rolling three-second window and return the standard
  too-many-attempts error when exceeded.
- Limits must block abusive repetition without rejecting a legitimate 500-player
  classroom burst from one NAT address.

### NFR-4.5: File Uploads

- Only authenticated hosts may upload files.
- The server must enforce an allowed content-type list and verify file signatures;
  a declared type that does not match the bytes must be rejected.
- Maximum size must be enforced by both multipart/form limits and application
  validation.
- Storage names must be generated by the server with an extension derived from
  the validated type. Client filenames must never determine a filesystem path.
- Uploaded files must be served with their correct image content type, without
  directory browsing or executable-content handling.
- Storage must remain behind `IFileStorage`. The current Azure VM deployment must
  mount durable upload storage; a multi-instance deployment must use shared object
  storage or an equivalent shared implementation.

## Verification

- Exercise authentication throttling, authorization boundaries, participant
  session validation, invalid upload signatures, oversize uploads, forwarded-IP
  handling, and secret redaction.
- Security checks must include requests through the production proxy, not only
  direct requests to the application container.
