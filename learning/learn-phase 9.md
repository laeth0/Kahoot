| Concept | Brief Meaning |
|---|---|
| **In-Memory Scoring with Zero Disk I/O ($p99 \le 5\text{ ms}$)** | Evaluating the entire speed-scaled scoring formula against pre-loaded snapshot data in process memory without touching disk or making additional database calls, meeting a $p99 \le 5\text{ ms}$ latency SLO per accepted answer. |
| **Non-Serializing Per-Answer Transactions** | Structuring the answer insert and score update transactions so that parallel submissions from different participants do not serialize behind a single lock, allowing concurrent throughput for 500 simultaneous answerers. |
| **Checked 64-Bit Arithmetic on Cumulative Score** | Storing `TotalScore` as a signed 64-bit integer (`BIGINT`) and computing all point additions using overflow-checked arithmetic (`checked(total += points)`) to prevent silent integer wrap-around across high-score multi-question games. |
| **Negative Response-Time Clamping (Clock Anomaly Guard)** | Clamping server-computed response time to a minimum of `0` before applying the scoring formula, preventing clock anomalies or sub-millisecond database timestamp jitter from awarding more than 100% of base points. |
| **Deterministic Multi-Level Tie-Breaker Tuple** | Sorting leaderboard rankings by a stable three-key tuple — `(TotalScore DESC, NormalizedNickname ASC, ParticipantId ASC)` — so identical scores always produce a unique, reproducible ordering without non-deterministic sort instability. |
| **Leaderboard Materialization Latency SLO ($p95 \le 100\text{ ms}$ / 500 Players)** | Sorting and materializing all 500-player rankings in a single in-memory or indexed database operation that meets $p95 \le 100\text{ ms}$, achieved by reading pre-aggregated per-player `TotalScore` rows rather than re-scanning all answer rows. |
| **`IsRemoved` Predicate Filtering Under Read-Committed Transaction** | Applying the `WHERE IsRemoved = false` filter inside a `READ COMMITTED` transaction during leaderboard materialization so that a concurrent kick committing between the start and end of the query is consistently excluded or included based on transaction snapshot. |
| **Server-Authoritative Score — Client Field Rejection** | Discarding any `points` or `score` fields present in client payloads at the deserialization boundary, so the scoring engine runs exclusively on server-side snapshot data and client manipulation has zero effect. |
| **Provisional Score Withholding During Active Question** | Excluding provisional points earned on the current active question from all leaderboard payloads and reconnect catch-up responses during `QUESTION_ACTIVE`, preventing early score inference before the reveal phase. |
| **Unique Constraint as Double-Scoring Prevention** | Relying on the database `UNIQUE(GameId, QuestionId, ParticipantId)` constraint as the ultimate guard against double-scoring, making the uniqueness enforcement structural rather than dependent on application-layer retry logic. |
