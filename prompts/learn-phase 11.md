| Concept | Brief Meaning |
|---|---|
| **SHA-256 Token Hash Lookup on Reconnect** | Looking up the reconnecting participant by computing `SHA256(sessionToken)` and querying the indexed `TokenHash` column, so the raw token is never stored and bulk table scans are avoided through an index seek. |
| **Indexed Token Hash Column for Burst Recovery** | Creating a database index specifically on `ParticipantSessionTokens.TokenHash` so that 5,000 simultaneous reconnect requests each resolve in a single index seek rather than a full table scan, preventing connection pool exhaustion during thundering-herd events. |
| **Atomic Connection Generation Increment** | Atomically incrementing a `ConnectionGeneration` counter on each successful reconnect in the database or session store, so that the new generation becomes the only accepted authoritative connection and all older connections are fenced without race conditions. |
| **Stale Disconnect Callback Discard (Connection ID Verification)** | Checking the departing `ConnectionId` in every disconnect handler against the participant's currently registered `ConnectionId` before acting on it, ensuring that a delayed disconnect event for an old socket never evicts the newer, active replacement socket. |
| **Connection Generation Fencing on Answer Submission** | Rejecting answer submissions from sockets whose `ConnectionGeneration` does not match the participant's current persisted generation, preventing a stale tab from committing answers after a newer reconnection has taken over. |
| **5,000 Reconnections in 60 Seconds ($p95 \le 3.0\text{ s}$)** | Supporting mass session recovery after a network hiccup or rolling restart at a throughput of 5,000 reconnects within 60 seconds while meeting $p95 \le 3.0\text{ s}$ per reconnect, achieved through indexed lookups, in-memory session caches, and client-side jitter. |
| **Jittered Client Backoff Against Thundering Herd** | Requiring clients to apply randomized exponential backoff (e.g., 0–5 seconds) before attempting reconnection after mass disconnection, spreading 5,000 concurrent reconnect attempts across time and preventing DB connection pool saturation. |
| **Phase-Matched Authoritative State Catch-Up Projection** | Constructing a different minimal catch-up payload for each game phase (`LOBBY`, `QUESTION_ACTIVE`, `QUESTION_RESULTS`, `LEADERBOARD`, `FINISHED`) from a single authoritative database read, returning only the fields needed for that phase without over-fetching. |
| **Pre-Reveal Correctness Withholding on Active-Question Catch-Up** | Excluding `isCorrect` flags and provisional points from the `QUESTION_ACTIVE` catch-up payload even when the reconnecting player has already answered, identical to the live broadcast payload rules, so reconnect does not become an early-reveal side channel. |
| **Session Reconnect as Zero-Seat-Reallocation Operation** | Treating reconnect as a pure socket rebinding that associates a new `ConnectionId` with an existing `Participant` row, explicitly never allocating a new seat or creating a new participant record, preventing double-seat use when rejoining a full game. |
