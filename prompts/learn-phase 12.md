| Concept | Brief Meaning |
|---|---|
| **Ordered Startup Phases with Fail-Fast Validation** | Executing container initialization in a strict sequential pipeline (config validation → migration → seeding → traffic readiness) so that any misconfigured secret or failed migration causes a hard fail before any traffic is accepted, rather than silently starting a broken process. |
| **`pg_advisory_xact_lock` as Single Migration Coordinator** | Acquiring a PostgreSQL transaction-level advisory lock before running any DDL so that exactly one replica executes migrations while peers block and then verify the schema version upon lock release, preventing concurrent DDL conflicts during multi-instance rolling starts. |
| **Bounded DDL Lock Timeout (`SET lock_timeout = '5s'`)** | Prepending `SET lock_timeout = '5s'` to every DDL migration statement so that a migration waiting for an exclusive table lock aborts after 5 seconds instead of creating a query queue that starves all application traffic (lock convoy). |
| **Expand/Contract Migration Strategy** | Splitting breaking schema changes into two sequential deployments — first expand (add new column/table, keep old), then contract (remove old after all instances are updated) — so that old and new application code can run concurrently against the same schema during rolling deploys. |
| **Nullable/Default Column Additions (No Unbounded Table Rewrites)** | Requiring that new columns be added as `NULL` or with a constant default that PostgreSQL 11+ can store as a catalog entry rather than rewriting every row, making the DDL an O(1) metadata operation instead of an O(N) table-scan lock. |
| **Zero-I/O Liveness Probe ($p99 \le 50\text{ ms}$)** | Implementing `/health/live` to verify only event-loop or thread-pool responsiveness with no I/O, no database calls, and no network calls, so a database outage never restarts an otherwise healthy process via liveness failure. |
| **Anti-Amplification Readiness Probe (3-Second Cached Result)** | Caching the readiness probe result for 3 seconds and coalescing concurrent probe requests behind a single active dependency check, preventing hundreds of Kubernetes readiness pings from multiplying DB connection pressure during a database degradation event. |
| **Health Probe Information Sanitization** | Returning only simple status strings (`"Healthy"`, `"Degraded"`, `"Unhealthy"`) from health endpoints with zero database hostnames, schema version numbers, stack traces, or exception details disclosed to callers. |
| **Worker Criticality Classification (Best-Effort vs. Correctness-Critical)** | Classifying background workers into two tiers — maintenance (best-effort, yield under load) and finalization (correctness-critical, SLO-bound) — so that failing maintenance workers do not trigger production alerts, while failing finalization workers escalate and mark readiness as `Degraded`. |
| **`FOR UPDATE SKIP LOCKED` in Multi-Replica Worker Isolation** | Selecting candidate rows with `FOR UPDATE SKIP LOCKED` in background worker queries so that multiple running replicas each claim non-overlapping row batches without deadlocking or processing the same row twice. |
| **Background Worker Exponential Backoff on Failure** | Catching all unhandled exceptions in hosted background services, logging them with full context, and entering exponential backoff (e.g., 10s → 30s → 60s) rather than crashing the hosting process, keeping the application alive during transient dependency failures. |
| **Graceful 30-Second Drain on `SIGTERM`** | On receiving a termination signal: (1) immediately returning `503` on `/health/ready`; (2) stopping new socket acceptance; (3) waiting up to 30 seconds for in-flight HTTP requests to complete; (4) sending `1001 Going Away` to all WebSocket connections before process exit. |
| **Structured JSON Log Redaction (Mandatory Fields)** | Mandating that passwords, password hashes, raw tokens, `Authorization` headers, `access_token` query parameters, cookie values, and database connection strings are stripped or masked before any log record is emitted to `stdout`/`stderr` or the OTLP pipeline. |
| **Vendor-Neutral OTLP Telemetry Pipeline** | Exporting all three observability signals (traces, metrics, structured logs) exclusively via standard OTLP (HTTP/protobuf) to an OpenTelemetry Collector, keeping the application code free of direct SDK dependencies on Prometheus, Jaeger, Loki, or any vendor-specific client library. |
| **Telemetry Failure Independence** | Using bounded, non-blocking in-memory export queues in the OpenTelemetry SDK so that Collector unavailability, backpressure, or crashes drop telemetry records silently without affecting application readiness, throughput, or the local `stdout` log stream. |
| **Health Probe Trace Filtering** | Excluding `/health`, `/health/live`, and `/health/ready` endpoints from distributed tracing instrumentation at the ASP.NET Core layer, preventing high-frequency probe spans from inflating trace storage and overwhelming the sampling budget. |
| **Parent-Based Ratio Trace Sampling** | Configuring production distributed tracing with `parentbased_traceidratio` sampling so that traces are sampled at a configured ratio (e.g., 10%) while respecting parent span sampling decisions, preventing trace storage saturation under production load. |
| **`traceId` Injection into ProblemDetails Responses** | Including the active OpenTelemetry `traceId` as a field in every RFC 7807 ProblemDetails error response, enabling a developer or support engineer to correlate a client-reported error directly to a Jaeger trace span and Loki log entries without manual log-grep. |
| **Strict Metric Label Low-Cardinality** | Prohibiting dynamic high-cardinality values (session tokens, game PINs, player IDs, individual answer IDs, timestamps) from being used as metric dimensions or log index labels, preventing metric cardinality explosion that degrades Prometheus query performance and Loki index size. |
| **Worker DB Connection Budget (Max 5 Connections)** | Reserving a bounded slice (e.g., 5 connections) of the total database pool for background workers, preventing maintenance work from competing with real-time request processing for database connections under peak load. |
