| Concept | Brief Meaning |
|---|---|
| **Two-Phase Suspension Architecture** | Splitting a heavy cascading operation into an immediate lightweight transactional cutoff (Phase 1) and a bounded asynchronous background materialization (Phase 2) to avoid long-running transactions, lock contention, and connection pool exhaustion. |
| **Logical vs. Physical Termination (Logical Cutoff)** | Immediately marking resources as terminal in application-layer guards at commit time, without waiting for background workers to physically update all child rows — preventing any new operations on logically-dead resources during the materialization window. |
| **Bounded Resumable Background Sweeps** | Processing large cascading updates in small, fixed-size database transactions (e.g., $\le 10$ rows per batch) with `SKIP LOCKED` semantics so that worker crashes are safe to resume from any checkpoint without re-processing already-committed batches. |
| **Optimistic Concurrency via Revision Number** | Attaching a monotonically incrementing `revision` integer to every mutable entity and requiring the client to supply the current value on writes; the server rejects stale writes with a `409` conflict, eliminating lost-update races without long-held locks. |
| **Immediate Real-Time Socket Eviction** | Broadcasting revocation events across all cluster instances via a pub/sub bus and forcefully closing affected WebSocket/SignalR connections within a bounded latency SLO ($p95 \le 500\text{ ms}$) on account suspension. |
| **Revocation Propagation SLO Across Cluster** | Guaranteeing that any credential or session invalidation (e.g. suspension, token version bump) is enforced on every node within $p95 \le 100\text{ ms}$ by distributing revocation events through a shared in-memory or message-bus channel. |
| **Administrative Keyset Prefix Search** | Combining keyset cursor-based pagination with a `NormalizedUsername` prefix filter and a composite B-tree index so that large account table scans complete in $p95 \le 150\text{ ms}$ without `OFFSET`-induced performance degradation. |
| **Transactional Last-Record Guard** | Using a `SELECT COUNT(*) ... FOR UPDATE` check inside the same transaction as the mutation to prevent concurrent requests from together violating a "at least one must remain" invariant (e.g., sole active administrator). |
| **Asynchronous Work Acknowledgment (202 vs. 204)** | Returning `202 Accepted` with a machine-readable in-flight flag (`terminationPending: true`) when background work is queued, allowing clients to poll for completion and enabling idempotent retries that distinguish "committed but pending" from "not yet committed". |
