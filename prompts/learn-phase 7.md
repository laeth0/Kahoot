| Concept | Brief Meaning |
|---|---|
| **Client-Generated UUIDv4 Idempotency Key (Join)** | Requiring the client to supply a high-entropy, unpredictable UUIDv4 `JoinOperationId` on the join request, stored hashed (`SHA-256`), so that a network-lost response can be safely retried without double-allocating a seat or double-issuing a session token. |
| **Hash-Only Storage of One-Time Credentials** | Storing only `SHA256(RawToken)` and `SHA256(JoinOperationId)` in the database — never the raw values — so a database read alone cannot be used to impersonate a player or replay a join operation. |
| **Active WebSocket Connection Generation Fencing** | Tracking an active connection "generation" counter per participant so that a late-arriving join retry does not invalidate or replace a session token that is already actively in use on an open socket — preventing accidental self-eviction. |
| **`SELECT FOR UPDATE` Seat-Counter Lock** | Acquiring an exclusive row lock on the seat counter inside the join transaction so that concurrent join races cannot both read "499 seats taken" and both successfully commit seat 500, enforcing the hard capacity ceiling atomically. |
| **Decoupled Transient Presence vs. Durable Seat Records** | Storing permanent seat allocations and participant identities in relational rows while tracking ephemeral WebSocket connect/disconnect events in a separate in-memory or distributed cache layer, avoiding row-level write amplification on every socket heartbeat across 25,000 concurrent connections. |
| **Monotonic Presence Version (Stale-Event Guard)** | Incrementing a monotonic `PresenceVersion` on every authoritative change (join, kick, reconnect) so that a delayed or out-of-order disconnect event arriving after a reconnect cannot clear the newer generation's presence state. |
| **NAT-Aware Token-Bucket Rate Limiting** | Sizing per-IP rate-limit buckets large enough to accommodate simultaneous burst joins from an entire classroom sharing one NAT IP (e.g., 500 students → 1,200 token capacity, 600 token/10s refill) without triggering false throttling. |
| **Strict Temporal Token Validity Boundary** | Enforcing a precise `serverTime < expiresAt` comparison (not `<=`) with no grace margin for session token validity, so the expiry instant is deterministic and consistent across all cluster nodes using synchronized UTC clocks. |
| **Token Cleanup Without Historical Data Deletion** | Scheduling expiration and deletion of session token hashes independently from the business data rows they reference (participant records, answers, scores), ensuring that credential cleanup does not cascade into historical data loss. |
| **Transactional Nickname Uniqueness with Tombstone** | Enforcing `UNIQUE(GameId, NormalizedNickname)` at the database level and never deleting the uniqueness record even after participant removal, so the constraint remains enforced for the entire game lifetime without application-layer re-checking. |
| **1,500 Joins/Second Platform Burst with Sub-Second Latency** | Sustaining 1,500 concurrent join requests per second across all lobbies at $p95 \le 500\text{ ms}$, and filling a single 500-seat lobby in under 5 seconds, achieved through bounded transactional seat locking and efficient index lookups. |
